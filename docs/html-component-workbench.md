# 规格：HTML 原型组件拆分工作台与单文件 AI 交接

历史发布记录：[GitHub Issue #29](https://github.com/leiyihai/MyFigma/issues/29)，发布时标签为 `ready-for-agent`。

**本文是 Issue #29 发布时的历史规格快照。以下自“问题陈述”起的全部正文及编号原样保留，仅作历史背景；其中“目前”“当前尚无实现”、流程与验收要求均属于当时语境，不是当前实现状态或本轮验收声明。** 本次仅补充此说明，未修改或发布 Issue，也不将新决定冒充已更新的 Issue 或新发布规格。

当前工作台定位、能力和限制见[工作台 README](../tools/html-component-workbench/README.md)；当前项目流程与拆分判断见[组件拆分判断规范](../.agents/skills/ui-design/references/component-decomposition.md)及其所属技能。历史正文不凌驾于新的流程决定；实现接口与 v1 数据结构见 README 所链接的契约及代码。

## 问题陈述（Problem Statement）

设计者目前先向 AI 提供需求，得到可交互 HTML 原型，再由 AI 搭建 Figma。原型的视觉和交互可以满足沟通需要，但 AI 对组件边界与维护方式的判断并不可靠：同一种家园卡片因尺寸、内容或位置不同被重复创建；外观相似的按钮又可能被合并，而设计者实际希望其中一个独立维护或成为不同变体。设计者不得不在 Figma 中进行二次拆分、合并和调整，既增加工作量，也影响后续换皮与实例同步。

设计者需要在进入 Figma 前亲自表达“哪些内容构成组件、哪些独立维护、哪些属于同组变体、哪些内部结构需要共用”，并直接看到组件之间的关联。这些决定必须与完整原型一起保存在可继续整理、可由 AI 读取的文件中，而不是只存在于聊天描述、截图或浏览器临时状态中。

## 解决方案（Solution）

交付独立本地网页工作台，承载按接入约定生成的 HTML 原型，提供预览和编辑两种模式：

**向 AI 提供需求 → AI 生成 HTML 原型 → 设计者使用工作台整理组件 → 保存整理后的单个 HTML 项目文件 → AI 读取该文件搭建 Figma，还原原型视觉并遵守人工组件关系。**

- 预览模式保留原型交互，用于检查操作路径及反馈。
- 编辑模式暂停业务交互和自动变化，允许直接切换预置界面及状态，选择、加选、减选内容，临时显隐检查后提取独立组件稿。原型本身的布局、层级与交互不被拆分操作改写。
- 左侧采用「界面／组件」TAB，中央显示原型、组件关系概览或独立组件预览，右侧提供当前选区与组件操作。不使用下拉菜单选择界面。
- 组件稿保留所选内容的视觉、文字、图片和可读取结构；工具完成必要的容器、层级与样式整理，不以整张截图代替组件内容。
- 是否复用由设计者决定，不自动去重。多选归组时第一个选中项为主体，其余为变体；主体是默认外观和结构参考，不是其他变体自动继承全部修改的父组件。
- 组件关系使用分组框和引用线表达：主体与变体放入同一组件组，嵌套引用由使用方指向被引用组件；选中时高亮引用方和相关线，弱化无关线。
- 保存单个 HTML 项目文件，完整携带原型、组件稿、样式与资源、来源对应、组件组和嵌套关系。文件可在普通浏览器查看，也可重新载入工作台继续整理，并为后续 AI 提供明确的结构化依据。

本规格交付到工作台及其真实文件产物。实际调用 AI／Figwright 写入 Figma、检查真实主组件／实例关联及客户端渲染，不是本规格的验收条件。

## 用户故事（User Stories）

### 接入、预览与界面切换

1. 作为界面设计者，我希望在独立本地网页中打开工作台，以便不连接 Figma 或某个聊天工具也能整理原型。
2. 作为界面设计者，我希望载入按工作台约定生成的 HTML 原型，以便把 AI 产出的原型直接接入整理流程。
3. 作为原型制作者，我希望有明确的界面、状态、节点标识和模式切换接入约定，以便生成能被工作台可靠定位和冻结的原型。
4. 作为界面设计者，我希望未适配或不兼容的原型得到明确提示，以便不会把工具无法定位的内容误认为已正确接入。
5. 作为界面设计者，我希望预览模式保持原型原有交互，以便检查操作路径、反馈和内容变化。
6. 作为界面设计者，我希望进入编辑模式后暂停按钮、键盘等业务输入和轮播、计时器、动画等自动变化，以便稳定选择当前画面。
7. 作为界面设计者，我希望在编辑模式直接切换预置页面和状态，以便无需反复回预览模式打开弹窗或走完整操作路径。
8. 作为界面设计者，我希望左侧「界面」TAB 按页面分组直接列出状态入口，以便通过点击而非下拉菜单快速切换。
9. 作为界面设计者，我希望从编辑返回预览后原型仍可正常操作，以便确认拆分过程没有破坏原型。
10. 作为界面设计者，我希望切换界面和工作台视图不会丢失已整理成果，以便连续处理多个页面。

### 选择、检查与独立提取

11. 作为界面设计者，我希望悬停时看到目标描边、点击后看到明确选中反馈，以便知道工具将提取哪些内容。
12. 作为界面设计者，我希望逐级扩大或缩小选区，以便在文字、信息栏和完整卡片之间选择所需边界。
13. 作为界面设计者，我希望加选多个所需元素，以便把原本分属不同父层级的内容整理为一个组件稿。
14. 作为界面设计者，我希望从当前选择中减去不需要的内容，以便不把附近图标、装饰或按钮误收入组件。
15. 作为界面设计者，我希望一键临时隐藏和恢复选中内容，以便检查漏选、错选及其实际覆盖范围。
16. 作为界面设计者，我希望临时检查不会永久删除内容或改变原型布局，以便检查结束后仍有完整原型。
17. 作为界面设计者，我希望由工具将所选内容包成独立组件稿并整理必要层级，以便不必手工再搭建一遍。
18. 作为界面设计者，我希望提取后字体、颜色、间距、图片、层叠和裁切等视觉表现保持一致，以便组件稿看起来确实来自原型。
19. 作为界面设计者，我希望组件稿中的文字、图片和结构分别保留，以便 AI 能读取并还原可编辑结构，而不是重画截图。
20. 作为界面设计者，我希望无法保持视觉的内容得到清楚提示，以便不会在不知情的情况下接受错位或截图降级。
21. 作为界面设计者，我希望提取操作不重排原型自身的层级、布局或交互，以便拆分结果与原型相互独立。
22. 作为界面设计者，我希望为组件稿命名并找到其来源页面、状态和位置，以便之后复核或重新调整提取范围。
23. 作为界面设计者，我希望在中央画布独立放大检查组件稿，以便发现缩略图看不出的漏背景、错层级或内容移位。
24. 作为界面设计者，我希望从组件稿定位回来源并返回原界面，以便对照组件与完整原型。

### 组件组、主体与变体

25. 作为界面设计者，我希望每次提取是否独立保留、合并或归组都由我决定，以便工具不会根据相似外观替我做维护决策。
26. 作为界面设计者，我希望同样外观的两个按钮也能保持独立组件，以便未来分别换皮和修改。
27. 作为界面设计者，我希望大小或内容不同的卡片可以按我的决定复用同一组件，以便不会因展示差异产生多余维护源。
28. 作为界面设计者，我希望在组件列表多选后定义它们属于同一个组件组，以便明确表达同组件的不同变体。
29. 作为界面设计者，我希望工具按实际选择顺序把第一项作为主体，以便我能够决定默认外观和比较基准。
30. 作为界面设计者，我希望其他选中项被明确标记为变体，以便不会被误认为无关的独立组件。
31. 作为界面设计者，我希望主体身份本身不触发所有变体自动同步，以便同组关系不会被误解为继承关系。
32. 作为界面设计者，我希望同组主体和变体能并排检查，以便比较结构及视觉差异。
33. 作为界面设计者，我希望能够修正自己建立的组件组和引用关系，并在影响已有关系时得到提示，以便误操作不迫使我从头整理。

### 嵌套复用与关系可视化

34. 作为界面设计者，我希望显式指定一个组件稿引用另一个组件稿，以便卡片、统计条或按钮等结构可按我的意图共用。
35. 作为界面设计者，我希望重叠选区不会自动建立嵌套关系，以便工具不会把相同来源误当作共用决定。
36. 作为界面设计者，我希望进入「组件」区域时默认看到关系概览，以便首先理解关系，而不是只看到孤立缩略图。
37. 作为界面设计者，我希望同组主体与变体显示在同一分组框内并有清楚标识，以便直接看出谁属于同一组件。
38. 作为界面设计者，我希望嵌套引用线从使用方指向被引用组件并标明「引用」，以便方向和含义不会产生歧义。
39. 作为界面设计者，我希望主体与变体不被画成父子继承线，以便视觉表达与实际更新规则一致。
40. 作为界面设计者，我希望选中组件后高亮引用它的组件及相关连线，以便判断一次修改可能影响哪些组件稿。
41. 作为界面设计者，我希望无关连线被弱化，以便组件变多后仍能读懂重点关系。
42. 作为界面设计者，我希望可从关系概览进入独立预览并返回概览，以便在整体关联与具体视觉之间切换。
43. 作为界面设计者，我希望共享组件稿更新前能查看影响范围，以便不会无意修改其他组件。
44. 作为界面设计者，我希望显式嵌套引用的共用结构随来源组件稿更新，以便一次整理能反映到实际使用方。
45. 作为界面设计者，我希望引用位置各自的文字、数值等内容差异在同步后保留，以便共用结构不会抹掉具体内容。
46. 作为界面设计者，我希望无法安全保留差异的更新先提示处理，以便不会静默覆盖已整理成果。
47. 作为界面设计者，我希望无效引用或无法安全展开的关系被明确阻止，以便项目始终能查看和保存。

### 保存、重新打开与原型改版

48. 作为界面设计者，我希望把整理成果保存为单个 HTML 项目文件，以便能直接携带、交接和重新打开。
49. 作为界面设计者，我希望保存文件包含完整原型而不仅是组件集合，以便 AI 仍可还原整个界面的视觉和上下文。
50. 作为界面设计者，我希望保存文件包含组件稿结构、样式、资源、命名、来源、主体／变体和嵌套引用，以便无需靠聊天重新描述关系。
51. 作为界面设计者，我希望在普通浏览器打开保存文件就能查看原型与组件成果，以便接收方不必先部署额外服务。
52. 作为界面设计者，我希望在全新工作台会话载入保存文件后继续整理，以便项目不依赖旧浏览器缓存或临时状态。
53. 作为界面设计者，我希望重新打开后的图片和样式仍完整，以便文件不会依赖已经失效的临时资源地址。
54. 作为界面设计者，我希望原型改版时保留已有组件稿与人工决定，以便不会因替换原型而从头整理。
55. 作为界面设计者，我希望看到改版后来源已变化或失效的内容标记，以便有针对性地复核，而不是接受工具猜测覆盖。
56. 作为界面设计者，我希望损坏或不支持版本的项目文件得到明确错误且不破坏当前成果，以便能够安全恢复工作。

### AI 交接与复用确认

57. 作为后续搭建的 AI 使用者，我希望整理文件中有明确可读取的结构和关系数据，以便不必仅靠截图猜测组件边界。
58. 作为界面设计者，我希望人工确认的独立、同组和嵌套决定约束后续 AI 搭建，以便不会再次被静默合并或拆开。
59. 作为界面设计者，我希望 AI 对未逐一标注的相似位置只提出候选复用关系，以便不必逐个重复提取，也不失去最终决定权。
60. 作为界面设计者，我希望能批量确认或排除候选位置，以便高效形成真正的来源复用映射。
61. 作为后续搭建的 AI 使用者，我希望区分已确认映射和未确认建议，以便只有已确认关系成为必须遵守的搭建约束。
62. 作为项目维护者，我希望工具的浏览器和文件验收与真实 Figma 验收分开报告，以便文件可读不会被误称为设计稿已搭建成功。

## 实施决策（Implementation Decisions）

### 1. 独立工具边界

- 新增工作台能力，职责涵盖工具壳层、原型接入与模式控制、选择与组件提取、组件关系及引用更新、HTML 项目读写。可以在同一应用内组织，不引入额外运行服务来分割这些职责。
- 现有图集导入器和独立九宫格插件不是工作台宿主，不修改其资源导入、用途分类或九宫格业务行为。组件拆分关系与资源导入器的「人工标签」是不同概念。
- 交付物在本地浏览器中工作，不要求用户运行开发服务器或连接 Figma。开发和测试时采用什么构建组织方式不在本规格锁定范围内。
- 产品原型内容与工作台工具栏、侧栏分离。此次新增的工具界面不应被插入产品原型内部，也不因此普遍改写既有纯原型交付规范。

### 2. 原型接入契约

- 为原型、页面、状态与可选择内容提供稳定标识，定义可枚举的界面／状态入口、设计尺寸、必要资源及受支持能力。
- 定义预览／编辑切换和直接进入预置状态的适配能力；编辑模式冻结业务输入和自动变化，工具自身的导航与选择继续有效。退出编辑后仍可正常预览。
- 首版只承诺对满足接入契约的原型可靠工作。历史原型需显式适配；没有契约、不支持的内容或缺失能力不能假装已成功导入。
- 原型格式、原型内容版本与工作台项目格式版本分别表达，避免把原型改版误当作文件格式升级。
- 承载原型时隔离其脚本与工作台项目数据，验证必要的跨窗口消息，不把原型内容视为能控制工作台的指令。单文件保存不能使原型获得不必要的主页面权限。

### 3. 选择与保真提取

- 选取依据受支持的实际内容结构，不把任意矩形截屏作为组件。允许跨不同父层级选择内容，由工具重建组件稿所需的共同容器、相对几何、层叠与样式上下文。
- 显隐用于临时检查，应能恢复；提取和检查均不永久删除、移动或重新挂接原型节点来重写其业务结构。
- 提取结果保存可读取的文字、图片及结构化内容，继承样式、必要的 CSS 变量、定位／变换、裁切和层叠等视觉条件需要被保留或等效重建。不是要求沿用所有原始祖先包装，也不是将整个组件栅格化。
- 不支持的视觉条件或不能等效提取的内容必须清楚提示；已有原型与组件稿保留。不能用「成功」提示掩盖丢图、错层、位移或截图降级。
- 每份组件稿具有独立身份及来源对应；名字、外观相似或来源重叠不自动改变组件身份或创建复用关系。

### 4. 组件关系与更新契约

- 组件稿、组件组、主体身份、变体成员、嵌套引用、引用位置的内容差异和来源映射分开记录，避免仅靠名字或画面位置推断语义。
- 多选归组使用实际选择顺序而非列表排序确定主体。主体只是组内默认外观及结构基准；显式嵌套引用才承担共用结构同步。
- 关系概览和独立预览读取同一份项目关系数据。分组框、方向箭头及影响高亮必须与保存文件中的关系一致，不能只在画面上连线。
- 嵌套引用更新区分共用结构与引用位置的文字、数值等覆盖内容；先展示影响范围，再应用更新。不能可靠保留差异时不静默提交；拒绝、取消或失败时保留原数据。
- 阻止悬空、自引用及导致无法展开的循环关系；调整组件组、引用或组件稿前保护已有使用方，不通过自动解除关联来掩盖问题。
- 来源复用映射能够区分已确认、候选和明确排除的结果。外部 AI 可基于稳定来源标识提出建议；工具需支持设计者记录、批量确认或排除映射，但不要求首版内置模型推理服务。

### 5. 单 HTML 项目与改版保护

- 项目文件既是可在普通浏览器打开查看的 HTML，也是可重新载入工作台、供 AI 读取的版本化项目资料，不能只保存画面坐标、关系图截图或组件缩略图。
- 文件携带完整原型、原型入口与版本、组件稿内容／样式／资源、组件及组身份、主体和变体、嵌套关系及覆盖内容、来源对应、映射确认状态和需要复核的信息。
- 机器可读数据需要可发现、语义明确并有稳定标识；查看原型和组件不依赖执行 AI 指令，读取关系不依赖从 SVG 连线反推。
- 保存后的资源不能依赖旧会话的临时地址、仅存在浏览器缓存的数据、开发机绝对路径或不可携带的外部文件。原型合法交互脚本与项目资料应安全封装。
- 重新载入时验证格式、版本和关系完整性。损坏或不支持版本应说明原因且不覆盖当前项目；需要迁移时明确处理，不静默丢弃资料。
- 原型内容改版后保留既有组件稿与人工决定，基于稳定来源对应检查变化并标记受影响项；不按外观或不稳定序号猜测重绑。需要复核的映射不能冒充已确认仍有效。

### 6. 后续 AI／Figma 交接

- AI 输入以整理后的项目文件为核心，同时包含完整原型上下文和人工组件约束；不是要求设计者再手工复述一次拆分，也不是只交付组件截图。
- 原型决定界面视觉与交互上下文，人工确认数据决定组件边界和维护关系；发生冲突或资料失效时应指出，而不是静默推翻人工决定。
- 候选复用必须经设计者确认才成为搭建约束。该规则不意味着工作台自动合并相似组件，也不要求内置一个新的 AI 聊天产品。
- 后续 Figma 搭建仍遵循原有的版本确认、目标与范围授权、分批换皮和真实主组件／实例检查要求；本规格不授予现有设计稿写入权限。

## 测试决策（Testing Decisions）

### 用户已确认的最高层测试边界

以 **Playwright 操作真实工作台公开界面，并检查实际导入、下载、普通浏览器打开及新会话重新载入的单 HTML 项目文件** 作为一个主要验收边界。视觉、文件语义与引用更新均在这条真实用户流程中断言，不另造一套模拟提取算法的测试 API。

当前尚无工作台实现或可直接复用的工作台入口，因此这是为新工具新增的公开应用入口，而不是把现有插件改造成测试宿主。

### 什么是有效测试

- 测试用户能看到的行为和拿到的文件，不绑定私有类名、内部容器层数、辅助函数调用或具体序列化实现。
- 实际导入文件、点击／选择、触发下载并重新打开；不能只调用内存中的保存函数或验证「保存成功」文案。
- 原型、组件提取、组件关系与同步、文件读写均经同一公开入口测试。关系和文本的期望由受控样例预先定义，不调用被测算法生成期望。
- 视觉对比固定浏览器、设计尺寸、字体及资源就绪条件；比较原型内容和组件稿本身，避免瞬态选框、光标或工具面板干扰。出现有意义的结构、裁切或样式差异时不能仅靠放宽截图阈值通过。
- 同时检查组件仍包含可读取文字、图片及结构，并核对导出关系；整张截图即使视觉一致也不算通过。
- 测试使用按接入契约生成的受控样例，覆盖家园卡片、独立与同组按钮、统计条等代表性结构；不把未经确认的现有家园原型或实际 Figma 文件作为自动化必需输入。

### 必须覆盖的流程与故障

1. **接入与模式隔离**：兼容原型可进入；缺失必要能力明确提示。预览可交互；编辑冻结业务鼠标／键盘输入及自动变化，但界面／状态仍可直达；返回预览正常。
2. **来源不变性**：选择、临时显隐、提取、建立引用及组件稿更新前后，原型的布局、内容和业务交互不被破坏。
3. **保真提取**：跨不同父层级的内容，包含继承字体／颜色、CSS 变量、图片、定位变换、裁切及层叠；加选、减选、扩大／缩小、显隐检查和独立预览均可观察，提取前后视觉相符且结构保留。
4. **明确失败**：不支持的提取条件不会静默降为截图或破坏已有成果；错误信息指出限制，用户仍能继续其他工作。
5. **人工决定**：相似组件可独立存在，不自动去重；实际多选顺序决定主体；变体不因主体更新而被当作继承同步；重叠来源不自动形成嵌套。
6. **关系可视化**：组框和主体／变体标签、使用方指向被引用方的箭头、选择高亮、无关线弱化、独立预览与返回路径可用，保存语义与关系图一致。
7. **引用更新**：同一共享组件被两个组件稿引用，各自内容不同；更新前可查看影响，两处共用结构更新、各自文字／数值保留、原型不变。覆盖冲突、取消、无效引用与循环关系不产生部分提交。
8. **映射确认**：候选、确认与排除可区分且能批量操作；未确认候选不改写人工组关系，不被导出为强制复用约束。
9. **真实保存闭环**：下载一个 HTML，普通浏览器在新上下文直接打开；空白工作台重新载入后核对完整原型、组件视觉、组关系、来源、引用和覆盖值，继续整理后再次保存仍一致。不能依赖旧缓存、临时资源地址或开发机路径。
10. **改版与文件错误**：原型内容新增、变化、删除后保留已有组件稿并标记受影响项，不猜测覆盖；损坏／不支持格式、失效来源和无效关系有可见反馈且不覆盖当前项目。
11. **原型隔离**：原型脚本或伪造跨窗口消息不能擅自改写工作台项目数据或绕过人工关系确认。

### 仓库先例

- 独立九宫格插件已有直接打开真实构建 HTML、实际点击／拖动／输入并检查输出像素与消息语义的浏览器测试，可借鉴原生 HTML UI 的测试组织方式。
- 图集导入插件已有构建 UI 的真实浏览器流程、执行状态与取消反馈、公开 UI 操作后检查实际落盘文件，以及重新加载验证状态边界的先例。
- 两个插件已有嵌套窗口消息来源校验测试，可借鉴隔离思路，但不能照搬 Figma 专属来源规则。
- 当前这些先例不等于已有 HTML 导入／下载／新会话重开的工作台测试。新增闭环应使用真实工作台和文件，而不是 Figma RPC 替身来冒充最终验收。

### 完成判定与报告

工作台的核心流程可实际操作，视觉和结构均保留，人工关系可查看并落实到可携带文件，关闭重开后能继续整理；所有已承诺故障边界通过公开入口验证。报告区分通过、失败和未验证，不把工具文件可读描述成 Figma 已还原成功。

本次规格整理未运行工作台测试，也未搭建真实 Figma；上述内容是实施后的验收要求，不是已完成声明。

## 范围外（Out of Scope）

- 任意未适配 HTML、外部网站或任意 DOM／CSS／脚本的无条件兼容；现有全部历史原型的自动迁移。
- 完整图层拖拽、自由布局、样式属性编辑器、通用网页 IDE 或任意截图切块工具。
- 按相似外观自动去重、强制归组或静默改变人工边界；把主体身份实现成所有变体的自动继承。
- 为了显示关系图而额外承诺通用自由连线／流程图编辑器；本规格要求已有组件关系可视化及通过明确操作建立关系。
- 内置模型账户、密钥管理、AI 聊天服务、模型训练或 AI 自动识别算法；候选建议可来自外部 AI，工具交付明确的确认与文件承载能力。
- 自动向 Figma 写入、一键 HTML 转 Figma、真实设计稿重构，以及真实客户端视觉或主组件／实例关联验收。
- 自动全量搭建所有页面、状态或变体；取消原有的 HTML 满意确认、Figma 写入授权和分批换皮关卡。
- 改造既有图集导入、资源用途分类、九宫格生成或本地资源助手。
- 多人实时协作、云端项目同步、账号权限系统及长期历史版本服务。

## 补充说明（Further Notes）

- 本规格来自本轮逐项对齐，发布请求是整理与发布规格的授权，不代表已经实现工具或获准写入 Figma。浏览器公开操作与单 HTML 文件闭环的测试边界已由用户明确确认。
- 术语约定：组件稿是从原型选取内容后独立整理的设计稿；组件组包含一个主体和其他变体；主体是默认外观与结构参考；嵌套复用是组件稿之间显式建立的引用。它们不等同于已经生成的 Figma 主组件、组件集或自动继承关系。
- 用户提供的家园卡片和三个导航按钮用于说明复用意图问题，尚未读取对应 Figma 文件实际节点关联。本规格使用可控示例验证同类情形，不把原有设计稿视为授权测试场所。
- 未来真实 Figma 试搭应另行确认目标文件、修改范围、代表样例、视觉完成标准及组件复用检查；届时需要同时证明视觉还原与正确主组件／实例关系，不能只证明看起来相似。
- 实施阶段需提供足以让原型生成方与后续 AI 使用者遵循的接入和文件语义说明；不以新增一套聊天口令或人工补充说明替代文件中的明确结构。
