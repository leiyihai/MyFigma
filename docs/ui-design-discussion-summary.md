# 游戏 UI 技能包与工具包：讨论记录及 Skill 选择

本文件整理本次会话的最终决定、已完成工作和下一步入口，供人查阅及后续会话续接；**不是新的执行规范、正式开发 Spec 或发布授权**。细则只在下列链接的权威文档维护，工作树和运行结果优先于本记录中的状态快照。

## 1. 我们最终要做什么

项目定位为**服务游戏 UI 的技能包 + 工具包**，先解决 MyFigma 的实际任务，不先泛化成覆盖所有产品的设计平台。

- 技能决定任务、产出和停止点；工具负责预览、测量、呈现拆分结果或实际编辑，不反过来定义设计流程。
- 按用户可以独立发起的任务拆技能，不把每个工艺步骤都变成技能，也不要求每次走完整条链路。
- [AGENTS.md](../AGENTS.md) 保持短路由，技能按任务加载参考；共享含义单处维护，不把聊天记录、外部教程或研究报告再堆成一套全局规范。
- 设计台能力与客户端解耦：保留 DSH 专用工具，同时提供独立通用工具；两者对齐基本证据口径，不追求全部功能对等。

现行导航：[README](../README.md)、[项目入口](../AGENTS.md)、[共同约定](../.agents/skills/ui-design/references/common.md)。

## 2. 已确认的流程与边界

### 设计任务

主线是：**对齐方案并确认 → 制作和自查灰阶交互原型 → 等待体验 → 用户请求进入 Figma，确认具体版本与范围 → 首批换皮基线 → 人换皮 → 指定范围内增量补齐。**

独立任务可以接手已有成果，认可的静态设计稿也可直接进入 Figma 任务。明确局部修改只处理受影响部分；加载技能或切换阶段不等于取得修改授权。设计版本、范围和拆分验收信息已齐全时，可以在一次明确问答中确认，不机械增加重复确认。

- 新建游戏界面默认 1280×720；明确给出其他尺寸时优先采用。工具调用须传入尺寸，不能依赖设计台默认网页画幅，也不能把适屏缩放当作适配验证。
- 玩家文案可以显示；影响状态、停表、按钮可操作性的规则要模拟成行为；状态矩阵、数据结构、埋点和验收条文不直接抄进界面旁注。
- 渲染、尺寸测量、实际点击／状态迁移分别记录结果。缺某种能力就说明该项未验，不统一冒充通过或统一说没运行。
- 制作自查属于制作任务本身；独立只读检查不是必经的额外审批步骤。

细则：[界面对齐](../.agents/skills/ui-design/references/ui-alignment.md)、[HTML 制作](../.agents/skills/ui-design/references/layout-preview.md)、[原型工艺](../.agents/skills/ui-design/references/prototype-craft.md)、[工具适配](../.agents/skills/ui-design/references/studio-tools.md)。

### Figma：一个技能，两个分支

不新增两套重复技能，也不分“低质量版／完整版”。

| 分支 | 目的与停止点 | 依据 |
| --- | --- | --- |
| 首批搭建 | 一个代表主界面与够用的独立换皮源，检查和冻结后交给人换皮；不提前铺满全部状态 | [首批参考](../.agents/skills/ui-design/references/figma-initial.md) |
| 增量补齐 | 读取实际已换皮成果，只补指定缺口；新增独立美术源先确认，无新增源不要求再换皮 | [增量参考](../.agents/skills/ui-design/references/figma-expand.md) |

原来的 Figma 搭建教程已收缩为[换皮维护与验收约束](../.agents/skills/ui-design/references/figma-ui.md)：视觉布局沿用认可稿，不机械复制 HTML 容器，不强制根 Frame 或每层组件 Auto Layout。流式排列按收益使用 Auto Layout，叠放美术可用普通 Frame 和必要定位约束；已有稿不自动转换。保留真实组件复用、美术与文字分离、用户成果保护、范围内验证及新增源冻结。

### 组件工作台：AI 主拆，人验收与纠偏

最终选择是**保留工作台并调整定位**，不是删除工具，也不是继续要求人从零逐个圈选。

- AI 按规范先准备边界、命名、独立维护及共享关系；人看整体效果和关键边界，可整批接受。
- 不对时，人定位问题让 AI 重拆，或按需人工选区、归组、排除；保留人工纠偏和已确认关系，避免整份重生成。
- 工作台展示和承载检查证据；规范定义拆分标准。组件稿或 `confirmed` 字段都不等于已取得人工认可，更不等于 Figma 实例同步通过。
- 普通原型的预览无需适配组件工作台；只有进入该工具时才要求其协议。

**目标与实现分开**：现有工具支持选区提取、组、引用、映射、保存／载入及改版复核。合法完整 v1 项目 HTML 可整项目载入，但不是 JSON API 或增量合并；AI 预拆生产、反馈重拆接入和确认来源审计尚未接通完整闭环。

依据：[拆分规范](../.agents/skills/ui-design/references/component-decomposition.md)、[工具现状](../tools/html-component-workbench/README.md)、[现有契约](../tools/html-component-workbench/CONTRACT.md)。[Issue #29 本地快照](html-component-workbench.md)已标为历史背景，原正文保留，未在本轮发布或修改远端 Issue。

### DSH 插件与界面功能的取舍

历史上讨论过改造左侧入口，最终已否决 fork／link 本地设计台插件的路径。此前运行态确认过：本机 profile 禁用插件同名技能和设计模式，保留设计台本体与工具；这是当时的本机状态，不是项目通用前提，本次整理未重新检查或改 profile。

截图中“样式／主题／检查”的结论是：当前灰阶原型流程不依赖样式和主题编辑，检查仍有用；没有据此隐藏按钮、删除插件功能或要求维护插件分支。HTML 阶段的常规设计台操作限于预览、看渲染、量问题，不把插件三方向、风格卡等流程强加进来。

## 4. 日常任务该用哪个项目 Skill

| 你想做的事 | 入口 | 它在哪里停 |
| --- | --- | --- |
| 从需求开始走全流程 | [ui-design](../.agents/skills/ui-design/SKILL.md) | 串联任务，并遵守各阶段停止点 |
| 讨论布局、控件和关键交互，先不画 | [ui-design-align](../.agents/skills/ui-design-align/SKILL.md) | 方案摘要与确认状态 |
| 按确认方案制作／修改可交互 HTML | [ui-design-prototype](../.agents/skills/ui-design-prototype/SKILL.md) | 当前原型、检查与缺口，等待体验 |
| 只检查界面或拆分结果，先别改 | [ui-design-review](../.agents/skills/ui-design-review/SKILL.md) | 问题、位置和证据，不修稿 |
| 首批搭 Figma，或基于换皮成果补齐 | [ui-design-figma](../.agents/skills/ui-design-figma/SKILL.md) | 获准本批，不自动扩展下一批 |

DSH 可输入 `/ui-design-*` 或从技能菜单选择；Pi 的 `/skill:<名称>` 是另一种客户端语法。无需背命令，自然语言明确任务即可触发单项；总入口保留给主动选择。

**不要混淆**：通用 `/prototype` 是回答一个设计问题的抛弃式试验技能，其 UI 分支默认探索多个方向；本项目稳定交付灰阶交互稿用的是 `/ui-design-prototype`，不是用前者替换当前流程。

## 5. 工程／文档工作该用哪个 Skill

下列作用已对照本机技能正文，不是只按名称猜测。它们是按需路线，不是每项任务都要走一遍；用户专用入口是否显示，以当前客户端菜单为准。

| 情况 | Skill | 当前是否要执行 |
| --- | --- | --- |
| 整理这份记录、修改规范／技能 | `/writing-for-agents` | 本次已采用；维护引用与单一规则来源 |
| 组件工具下一步接口、反馈与验收还有关键分歧 | `/grill-with-docs`，内部用 `grilling` + `domain-modeling` | 仅讨论尚未定的工程问题，不重新问已确认定位 |
| 需要再查外部能力或技能依据 | `/research` | 需要新事实时再用；已有[研究记录](research/figma-building-skills.md)可直接参考 |
| 某个状态模型／UI 问题必须跑起来才判定 | `/prototype` | 有明确待回答的问题时才做受控试验，不冒充真实需求验收 |
| 把已确定的后续功能整理为正式规格 | `/to-spec` | 需先定范围与测试边界；该技能会发布到 Issue tracker，本次不触发 |
| 规格需要分多会话完成 | `/to-tickets` | 确认纵向切片、阻塞关系后才发布任务 |
| 按明确规格／Ticket 实现 | `/implement`，在约定测试边界驱动 `/tdd` | 新实现获准后再开始；该技能正文包含提交步骤，调用前要明确这一范围 |
| 正式工程审查 | `/code-review` | 先定固定比较基准和 Spec；当前未提交／未跟踪内容需明确纳入，不能只看已提交差异 |
| 换客户端、目录、协作者或迁移子任务 | `/handoff` | 确有迁移需要时，按技能写到系统临时目录；不是本地长期讨论记录的替代品 |

正式发布与任务操作遵循[GitHub tracker 约定](agents/issue-tracker.md)及[分流标签](agents/triage-labels.md)。仓库已有这些约定；本次没有创建 Issue、Ticket 或提交。

## 6. 下一步建议：先决定，不直接开工

优先把组件工作台的 AI 闭环变成一个明确可验收的小范围：

1. AI 预拆结果经什么公开入口交给工作台？现有完整项目文件能力能复用多少，需要新增什么？
2. 反馈重拆如何只更新受影响部分，并保留人工纠偏、稳定身份和已确认关系？
3. 人工整批验收的依据如何记录与追溯，避免状态字段冒充确认？
4. 最高层验收接口选哪里？优先沿用真实工作台公开 UI + 单 HTML 文件闭环，若新增接口，再确认其覆盖与遗漏；没有提前决定接口或更改 v1 格式。

建议路线：**围绕这些缺口 `/grill-with-docs` → 范围与测试边界明确后 `/to-spec` → 多会话才 `/to-tickets` → 获准后 `/implement` + `/tdd` → 指定基准的 `/code-review`。** 它不是要求重做已经完成的技能拆分与通用设计台。

另一项独立验证是：取得一小批真实 Figma 目标和授权，用当前首批／增量规则实际换一次皮，检查操作负担，再决定是否继续调整。不能只靠规范行数下降或工具测试通过宣称已经省工。
